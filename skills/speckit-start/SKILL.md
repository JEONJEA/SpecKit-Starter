# SpecKit-Start

Use the official `specify` CLI for scaffolding and integration management. End after setup and verification. Leave the SDD workflow to the installed Spec Kit skills.

## 1. Locate the CLI

1. Resolve `specify` and run `specify version` (on Windows, use `Get-Command specify -CommandType Application` and check `$LASTEXITCODE`). Require successful output identifying the Spec Kit CLI and its version. Keep the verified executable path for every subsequent command. If a resolved executable fails, investigate the error and the other installed candidates before considering installation.
2. When PATH lookup fails, inspect package-manager evidence. For uv, use `uv tool dir --bin`, `uv tool dir` and `uv tool list`. Check for `specify.exe` on Windows or `specify` elsewhere in the reported bin directory, even if `uv tool list` fails to acquire its lock. Check for a tool directory or receipt when the launcher is missing. Also inspect the user's configured tool bins (`UV_TOOL_BIN_DIR`, `PIPX_BIN_DIR`, or common locations such as `~/.local/bin`) and saved user/system PATH (which may differ from the current shell). Check pipx or Python installations if present (`pipx list`, `python -m pip show specify-cli`, and the corresponding scripts directories). If uv is unavailable on PATH, check its configured or usual user bin before concluding that it is missing.
3. Verify any launcher found outside PATH with its absolute path, then use that path. On PowerShell, use `& $SpecifyCli version`, with `$SpecifyCli` set to the full path. Tell the user how to refresh their terminal or correct PATH for future sessions. Do not edit persistent PATH. If evidence indicates a failed install or access was denied and absence cannot be established, report the ambiguity and stop before installing.
4. When no existing installation is found and uv works, ask the user to approve `uv tool install specify-cli` from the [official installation guide](https://github.github.com/spec-kit/installation.html). Run it only on explicit approval. Check the exit code, rediscover the launcher (including uv's bin directory), and verify its version. If uv is missing, link the [official uv setup](https://docs.astral.sh/uv/getting-started/installation/) and the Spec Kit installation guide. Leave prerequisite installation to the user. Never upgrade an existing CLI automatically.

## 2. Identify the project and desired integrations

- Use the Git top-level directory as the default project root, or the current workspace directory without Git. Resolve the absolute path. Inspect the current directory and its parents for closer Spec Kit state and check `SPECIFY_INIT_DIR`. If these indicate a different target (for example a monorepo member) or the root is ambiguous, ask which directory to use. Run all project commands with that working directory and suppress any conflicting `SPECIFY_INIT_DIR` only in the child process or temporary shell scope. Never change the user's persistent environment.
- Inspect `.specify/integration.json`, core templates/scripts, and agent files. If `.specify` exists, run `specify integration status --json`; also inspect `specify integration list` when needed. Evaluate the report and files together. An exit code of zero can include a warning. Check that the reported default and installed integrations agree with the recorded state, review relevant manifest findings, and distinguish modified files from missing or invalid files. Preserve customization. An empty, malformed, linked, legacy, or partially initialized `.specify` requires diagnosis. Never treat it as a clean target for `init`. Check recognizable legacy agent paths such as `.codex/prompts` and `.claude/commands` before declaring a fresh project. If the installed CLI cannot verify or safely add to legacy state, report the version and point to the [official upgrade guide](https://github.github.com/spec-kit/upgrade.html).
- On first setup, ask for **Codex + Claude Code**, **Codex only**, or **Claude Code only** (honor a choice the user already supplied). On an existing project, honor explicit targets. Otherwise target the host agent that invoked this skill. If the host is unknown and either integration needs work, ask which is wanted. When all desired integrations are already healthy, skip approval and all setup commands. If a desired integration is registered but broken, report the failing check and stop before reinstalling or upgrading it. Leave other installed integrations and the current default in place.

## 3. Preview and obtain project approval

Read the installed CLI's `init --help`, `integration status --help`, and, when needed, `integration install --help`. Verify the required options and each missing agent's runtime availability using the official [Codex](https://github.github.com/spec-kit/integrations/codex.html) or [Claude Code](https://github.github.com/spec-kit/integrations/claude.html) integration guide. If the CLI lacks the needed capability or an agent is unavailable, report it. Do not install agent applications or skip their prerequisite checks.

Use the version being run to determine the intended write paths. Explain the absolute root, missing integration(s), proposed commands, and potential writes. If Git shows tracked or untracked changes, recommend making a backup or committing first. Do not create commits or stashes on the user's behalf. Ask for explicit project approval, separate from CLI installation approval, before scaffolding or adding an integration. Refusal or an unavailable approval channel ends the mutation flow.

After approval, before touching the target, generate a preview in a fresh temporary directory by running the same `init` command there without `--force`. For a dual initial setup, add the second integration in the preview too. For an existing project, preview the missing agent's standalone scaffold to discover its agent-specific output paths, and cross-check the integration guide and project state for any other managed files the add operation touches. List all generated paths, including hidden files. Reject file collisions and symlinks, junctions, or file/directory conflicts in the affected paths or their parents. Existing ordinary parent directories are fine. For an add, shared Spec Kit files and current state/manifest metadata are expected to be present. The add may update official integration metadata to register the new agent. Proceed only when shared infrastructure is healthy, the target integration's output paths are unoccupied, and other existing content can be preserved. If the write footprint cannot be established or a preview fails, report the cause and stop. Clean up only your own temporary preview directory.

## 4. Apply only approved changes

Recheck the target path, integration status and collision checks just before each write. Use the verified CLI executable in place of `specify`.

- **New project:** `specify init --here --non-interactive --integration <key> --script ps "--integration-options=--events false"` on Windows. Use `--script sh` on Unix-like systems. Add `--force` only for a nonempty root when the installed CLI requires it and the approved plan includes it. This flag permits merging and can overwrite generated destinations, so the preview collision check is essential. For both agents, initialize once with `codex` and, after verification, add `claude` with the next command.
- **Missing integration:** `specify integration install <key> "--integration-options=--events false"` for `codex` or `claude`. Require the installed CLI to allow this combination without forcing multi-install. Keep the existing script variant and preserve the default integration. Do not run `integration use`, `switch`, `upgrade`, `uninstall`, or `init` here.

The events option keeps setup focused on the core skills and avoids registering native event handlers in agent settings. Preserve existing settings, shared templates and feature documents, including any custom spec directory. Never copy preview files into the project or bypass a CLI safety error.

Check the command's exit status before moving on. On failure, inspect status and the project diff, report the command, error and any partial changes, and stop. Never rerun a failed initialization on a partially written project or clean up project files automatically. If only the second agent failed after a successful first step, report the verified first integration and the incomplete second one.

## 5. Verify and report

- Confirm `specify version` and `specify integration status --json` from the selected root. Confirm readable shared infrastructure, installed/recorded state and valid manifests for desired agents. When adding to an existing project, confirm the default and previous integrations are still present. Report relevant warnings without masking missing or invalid state.
- Verify the actual skill files with valid frontmatter in `.agents/skills/speckit-<command>/SKILL.md` (Codex) and `.claude/skills/speckit-<command>/SKILL.md` (Claude Code). Use the valid files for `specify`, `clarify`, `plan` and `tasks` to decide which commands to show. For a verified legacy layout, report the invocation actually exposed by that layout. A registered integration alone does not prove file availability.
- Report under **[SpecKit-Start]** with the CLI version, absolute project path, project status, and status for each agent. Report readiness only when the requested setup is verified. Show available commands as `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks` for Codex, or the equivalent `/speckit-...` names for Claude Code. If files exist but the client does not list them, suggest reopening the agent from the project root (or `/reload-skills` in Claude Code when supported), and check file locations, trust and workspace settings if needed.
